# MTSCOS AI 项目开发规则

## 1. 开发原则

> **核心原则**：规范、安全、可维护、可扩展、巡检驱动

所有开发活动（新建功能、修改代码、维护增强）必须遵循本规则和《设计规范》。任何偏离规则的代码将被拒绝合并，并自动触发巡检引擎检测。

### 1.1 巡检驱动开发

| 原则 | 说明 |
|------|------|
| **巡检优先** | 所有代码变更必须通过 AI 巡检引擎检查 |
| **自动修复** | 检测到的问题自动触发修复流程 |
| **法律准则合规** | 所有开发活动必须遵循法律准则文件规定 |
| **错误上报** | 运行时错误自动上报到数据库 |
| **学习闭环** | 修复经验自动积累到脑库 |

#### 2.2.2 ⚠️ 新文件智能归档强制规则（IRON RULE）

> **此规则为强制规则，不可绕开，优先级等同于§14 IRON_RULE**

**任何新生成的文件必须按照以下决策树归档到正确的目录，严禁直接放置在根目录。**

##### 归档决策树

```
新文件生成时，按以下顺序判断归档位置：

Step 1: 文件是否为Flask入口/项目配置？
  ├─ 是 → flask-app/ 根目录（仅限app.py/server_real_db.py/version_manager.py/VERSION/Dockerfile/requirements*.txt）
  └─ 否 → Step 2

Step 2: 文件是否为AI引擎/Agent/自动化模块？
  ├─ 是 → ai_engines/（或其子目录brain/learning/management/security/monitoring/utils）
  └─ 否 → Step 3

Step 3: 文件是否为系统级引擎（性能/安全/教育/运维/前端增强）？
  ├─ 是 → engines/
  └─ 否 → Step 4

Step 4: 文件是否为业务服务（含业务逻辑）？
  ├─ 是 → services/（或app/services/）
  └─ 否 → Step 5

Step 5: 文件是否为API路由/蓝图定义？
  ├─ 是 → api/ 或 routes/（或app/api/）
  └─ 否 → Step 6

Step 6: 文件是否为核心基础设施（数据库/缓存/配置）？
  ├─ 是 → core/
  └─ 否 → Step 7

Step 7: 文件是否为运维脚本（部署/修复/升级/工具）？
  ├─ 是 → scripts/（或其子目录fix/upgrade/tools/）
  └─ 否 → Step 8

Step 8: 文件是否为HTML模板？
  ├─ 是 → templates/（按admin_app/student/mobile/分类）
  └─ 否 → Step 9

Step 9: 文件是否为测试文件？
  ├─ 是 → tests/unit/ 或 tests/integration/
  └─ 否 → Step 10

Step 10: 文件是否为静态资源？
  ├─ 是 → static/ 或 src/html/
  └─ 否 → Step 11

Step 11: 文件是否为集群/数据库工具/SDK/Nginx配置？
  ├─ 集群 → cluster/
  ├─ DB工具 → database/
  ├─ SDK → sdk/
  ├─ Nginx → nginx/
  └─ 否 → 报错：无法分类的文件，需人工确认归档位置
```

## 3. 代码规范

### 3.1 Python代码规范

#### 3.1.1 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 模块名 | 小写，下划线分隔 | `auth_service.py` |
| 类名 | 大驼峰 | `AuthService` |
| 方法名 | 小写，下划线分隔 | `get_user_by_id()` |
| 变量名 | 小写，下划线分隔 | `user_id` |
| 常量名 | 全大写，下划线分隔 | `MAX_RETRY_COUNT` |
| 蓝图名 | 小写，下划线分隔 | `admin_api` |

#### 3.1.2 代码风格

- 使用 **4空格缩进**（禁止使用Tab）
- 行宽不超过 **120字符**
- 每行一个语句，禁止多语句同行
- 使用类型提示（Type Hints）
- 模块级函数和类必须有文档字符串（Docstring）

#### 3.1.3 路由规范

```python
# 蓝图注册（app/routes/__init__.py）
from flask import Blueprint

admin_api = Blueprint('admin_api', __name__)

# 路由定义（app/routes/admin_api.py）
from . import admin_api
from app.services.admin_service import AdminService

@admin_api.route('/api/admin/users', methods=['GET'])
def get_users():
    """获取用户列表"""
    service = AdminService()
    users = service.get_users()
    return {'code': 200, 'data': users}
```

#### 3.1.4 模型规范

```python
# app/models/user.py
from app.extensions import db

class User(db.Model):
    """用户模型"""
    id = db.Column(db.Integer, primary_key=True)
    username = db.Column(db.String(64), unique=True, nullable=False)
    email = db.Column(db.String(120), unique=True, nullable=False)
    
    def to_dict(self):
        """转换为字典"""
        return {
            'id': self.id,
            'username': self.username,
            'email': self.email
        }
```

#### 3.1.5 服务层规范

- 路由层**不包含**业务逻辑，仅负责参数接收和响应格式化
- 业务逻辑必须放在**Service层**
- Service层可以调用其他Service，但禁止循环依赖

// 使用统一的API调用函数
async function apiRequest(url, options = {}) {
    const defaultOptions = {
        headers: {
            'Content-Type': 'application/json',
            'X-Requested-With': 'XMLHttpRequest'
        },
        credentials: 'same-origin'
    };
    
    const response = await fetch(url, { ...defaultOptions, ...options });
    const data = await response.json();
    
    if (data.code !== 200) {
        throw new Error(data.message || '请求失败');
    }
    
    return data.data;
}
```

## 4. 异常处理规范

### 4.1 异常体系

所有非系统级异常必须使用自定义异常类：

```python
from app.exceptions import (
    AppException,
    AuthenticationException,
    AuthorizationException,
    ValidationException,
    ResourceNotFoundException,
    BusinessException
)
```

### 4.2 异常使用场景

| 异常类 | 使用场景 | HTTP状态码 |
|--------|---------|-----------|
| `AuthenticationException` | 未登录、Token过期 | 401 |
| `AuthorizationException` | 权限不足 | 403 |
| `ValidationException` | 参数校验失败 | 400 |
| `ResourceNotFoundException` | 资源不存在 | 404 |
| `BusinessException` | 业务逻辑错误 | 400 |
| `AppException` | 通用业务异常 | 400 |

### 4.3 异常抛出示例

```python
from app.exceptions import ValidationException

def create_user(data):
    if not data.get('username'):
        raise ValidationException(
            message='用户名不能为空',
            error_type='VALIDATION_ERROR',
            suggestion='请输入用户名',
            details={'field': 'username'}
        )
```

### 4.4 异常处理

所有异常由 `ExceptionHandler` 统一捕获，返回标准格式响应：

```json
{

## 17. 数据库Schema兼容性规范

### 17.1 Schema变更原则

| 原则 | 说明 |
|------|------|
| 向后兼容 | 新增字段必须有默认值，不允许删除已有字段 |
| 字段映射 | 旧字段名与新字段名必须提供映射机制 |
| 迁移脚本 | 所有Schema变更必须有对应的迁移脚本 |
| 版本记录 | 记录每次Schema变更的版本号和变更内容 |

### 17.2 表结构兼容性处理

所有模型创建表时必须检测并兼容已有表结构：

```python
@classmethod
def _create_table(cls):
    """创建表（必须兼容已有结构）"""
    try:
        db_manager.execute(f"""
            CREATE TABLE IF NOT EXISTS {cls.TABLE_NAME} (
                id INTEGER PRIMARY KEY AUTOINCREMENT,
                name TEXT NOT NULL,
                description TEXT
            )
        """)
        cls._add_missing_columns()
    except Exception as e:
        logger.error(f"创建表失败: {str(e)}")

@classmethod
def _add_missing_columns(cls):
    """添加缺失的列（保持向后兼容）"""
    columns_to_add = [
        ('status', "TEXT DEFAULT 'draft'"),
        ('created_at', "TIMESTAMP DEFAULT CURRENT_TIMESTAMP"),
        ('updated_at', "TIMESTAMP DEFAULT CURRENT_TIMESTAMP")
    ]
    for col_name, col_def in columns_to_add:
        try:
            db_manager.execute(f"ALTER TABLE {cls.TABLE_NAME} ADD COLUMN {col_name} {col_def}")
        except Exception:
            pass
```

### 17.3 字段名变更规范

| 变更类型 | 处理方式 |
|---------|---------|
| 字段重命名 | 保留旧字段，新增新字段，提供映射 |
| 字段类型变更 | 使用ALTER COLUMN或创建新字段 |
| 字段删除 | 标记为deprecated，不物理删除 |

### 17.4 Schema迁移脚本

所有Schema变更必须有迁移脚本，放在 `scripts/migrations/` 目录：

```text
scripts/migrations/
├── 001_add_status_column.py
├── 002_add_created_at_columns.py
└── migration_log.json
```

## 22. 前端错误捕获规范

### 22.1 全局错误捕获

所有前端页面必须在base.html中实现全局错误捕获：

```javascript
// base.html - 全局错误捕获
window.onerror = function(message, source, lineno, colno, error) {
    reportError({
        type: 'javascript_error',
        message: message,
        source: source,
        line: lineno,
        column: colno,
        stack: error ? error.stack : '',
        url: window.location.href,
        userAgent: navigator.userAgent
    });
    return true;
};

window.addEventListener('unhandledrejection', function(event) {
    reportError({
        type: 'promise_rejection',
        message: event.reason ? String(event.reason) : 'Promise rejected',
        source: 'unhandledrejection',
        line: 0,
        column: 0,
        stack: event.reason ? (event.reason.stack || '') : '',
        url: window.location.href,
        userAgent: navigator.userAgent
    });
});

// 覆盖console.error
const originalError = console.error;
console.error = function(...args) {
    originalError.apply(console, args);
    reportError({
        type: 'console_error',
        message: args.map(arg => typeof arg === 'object' ? JSON.stringify(arg) : String(arg)).join(' '),
        source: 'console.error',
        line: 0,
        column: 0,
        url: window.location.href,
        userAgent: navigator.userAgent
    });
};

function reportError(errorData) {
    fetch('/api/ai_inspection/console_error', {
        method: 'POST',
        headers: {
            'Content-Type': 'application/json',
            'X-CSRF-Token': document.querySelector('meta[name="csrf-token"]')?.content || ''
        },
        body: JSON.stringify(errorData)
    }).catch(() => {});
}
```

| console.error调用 | 重写console.error | ai_inspection_console_errors |
| 网络请求错误 | fetch拦截 | ai_inspection_console_errors |

    description='考试创建必须绑定合法班级，禁止创建空班级考试',
    legal_basis='《MTSCOS考试管理办法》第5条',
    bypass_allowed=False,  # RED_LINE禁止跳过
)
def rule_exam_valid_class(exam_obj, user_container):
    """规则执行函数：返回 (passed: bool, message: str)"""
    if not exam_obj.class_id or not _class_exists(exam_obj.class_id):
        return False, '考试必须绑定合法班级'
    if _class_archived(exam_obj.class_id):
        return False, '班级已归档，禁止创建考试'
    return True, ''
```

## §15 AI反复修Bug四步法铁律 (v1.0.0 VIBE-DEBUG-IRON-RULE)

> **⚠️ 硬约束红线**：当AI在同一个Bug上反复修改仍未解决时，**必须执行本四步法**，不得继续在原对话中盲目重试。
> 来源：抖音《Vibe Coding术语》第45集《AI反复修不好一个bug怎么办？》 作者：敲代码的小虾米
> 发布日期：2026-08-05  视频链接：`https://v.douyin.com/uCRLWY9kNFY/`
> 规则版本：v15.0.0 新增

### §15.0 核心铁律

| 铁律编号 | 铁律内容 | 严重程度 |
|---------|---------|---------|
| **VD-1 (CRITICAL)** | 同一个问题让AI改到**第三次还没好**，就**别再让它试了**——立即踩刹车，执行四步法 | CRITICAL |
| **VD-2 (CRITICAL)** | 一轮完整的处理至少包含三件事：**提出原因、完成修改、重新走一遍出错过程**。缺任一件视为无效轮次 | CRITICAL |
| **VD-3 (HIGH)** | 换新对话时必须补一份**真源文档**，包含四要素（见§15.2） | HIGH |
| **VD-4 (HIGH)** | 翻老账时必须列出前三轮各自的原因、判断、修改内容、验证结果及未能解决的原因 | HIGH |
| **VD-5 (HIGH)** | 逼AI拿出**根因**，必须解释三点：为什么出现当前症状、为什么最早在这个位置观测到异常、为什么前三轮修改都没解决 | HIGH |
| **VD-6 (HIGH)** | 只改**证实过的那一处**，改完AI自己验，验证本次改动可能波及的正常功能 | HIGH |
| **VD-7 (MEDIUM)** | 四步法执行过程必须落库（mt_ai_debug_session 表），与§14开发流程关联 | MEDIUM |

### §15.1 踩刹车的时机 (00:39)

**触发条件**：同一个Bug，AI已经修改了**3次（含3次）以上**仍未解决。

| 判定标准 | 说明 |
|---------|------|
| **同一Bug** | 问题根因相同或症状相同，而非新产生的不同问题 |
| **3次未解决** | 3次修改后Bug仍然存在或引入新Bug |
| **立即停止** | 不得进行第4次盲目修改，必须转入四步法流程 |

> **禁止行为**：在原对话中继续输入"还是不行"、"再改改"、"还有问题"——这只会让AI陷入死循环。

### §15.2 第一步：换个新对话，补一份真源 (02:00)

**操作**：关闭当前AI对话，开一个全新对话，并提供一份**真源文档**。

真源文档必须包含以下四要素：

| 序号 | 要素 | 说明 | 示例 |
|------|------|------|------|
| ① | **本阶段要解决的问题** | 用一句话精确描述Bug现象 | "用户登录后token过期时间计算错误" |
| ② | **正常流程的预期运行路径** | 描述正确情况下代码应如何执行 | "用户登录→生成token→设置过期时间为24h→返回前端" |
| ③ | **不得变更的现有行为** | 列出不能动的功能/逻辑 | "token刷新机制不能改、session存储逻辑不能动" |
| ④ | **判定完成的验收标准** | 明确什么程度算修好了 | "登录后token过期时间=24h±0s，刷新后延长24h，无401错误" |

> **真源文档模板**（可直接复制使用）：
> ```
> ## Bug真源文档
> 【问题】<一句话描述>
> 【预期路径】<正常流程>
> 【不得变更】<现有行为清单>
> 【验收标准】<完成判定条件>
> ```

### §15.3 第二步：钉住问题，翻出前三轮真源 (03:37 + 04:31)

**操作**：在新对话中，把问题钉住不动，然后翻出前三轮的修改记录。

**翻老账清单**（每轮必须列全）：

| 轮次 | 记录项 | 说明 |
|------|--------|------|
| 第1轮 | 原因 | AI判断的Bug原因 |
| | 判断 | AI的分析逻辑 |
| | 修改内容 | 具体改了哪些代码 |
| | 验证结果 | 修完后Bug是否消失 |
| | 未能解决的原因 | 为什么没修好 |
| 第2轮 | 同上5项 | ... |
| 第3轮 | 同上5项 | ... |

> **目的**：让AI看到前三轮的完整尝试历史，避免重复犯同样的错误。

### §15.4 第三步：逼它拿出根因 (05:15)

**操作**：要求AI进行根因分析，必须回答以下三个问题：

| 序号 | 问题 | 说明 |
|------|------|------|
| ① | **为什么出现当前症状？** | Bug现象的根本成因 |
| ② | **为什么最早在这个位置观测到异常？** | 异常首次出现的代码位置及原因 |
| ③ | **为什么前三轮修改都没有解决？** | 前三轮各自的修改为什么无效 |

> **强制要求**：三个问题必须全部回答，缺一不可。AI不得跳过或模糊回答。

### §15.5 第四步：只改证实过的那一处 (07:46)

**操作**：基于根因分析，只修改**已经被证实的那一处**问题代码。

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 定位证实过的根因代码 | 只改根因分析中确认的那一处 |
| 2 | 只改这一处 | 不顺带改其他"看起来也有问题"的代码 |
| 3 | AI自己验证 | 改完后AI运行验证，确认Bug已修复 |
| 4 | 验证波及功能 | 检查本次改动可能影响的其他正常功能 |

> **禁止行为**：一次性改多处代码、改完不验证、不检查波及影响。

### §15.6 总结 (09:17)

```
AI反复修不好一个Bug → 四步法：
  ① 换新对话 + 补真源（问题/预期/不变/验收）
  ② 钉住问题 + 翻前三轮老账（原因/判断/修改/验证/未解决原因）
  ③ 逼拿根因（为什么出现/为什么在这里观测/为什么前三次没修好）
  ④ 只改证实过的那一处 + 自己验 + 验波及
```

### §16.4 AI报告安全问题的处理 (第44集)

> 来源：第44集《Vibe Coding问题篇：AI说代码有安全问题该咋办？》发布约2026-08-02
> 标签：#vibecoding #ai教程分享 #人工智能编程

**安全问题处理四步法**：

| 步骤 | 铁律 | 操作 | 禁止行为 |
|------|------|------|---------|
| 1. 验证 | VS-1 | 先验证AI报告的安全问题是否真实存在 | 禁止盲目相信AI的安全报告 |
| 2. 评估 | VS-3 | 分类处理：确认→评估影响范围→确定优先级 | 禁止不评估影响直接修复 |
| 3. 修复 | VS-2 | 最小范围修复，只改证实过的安全漏洞 | 禁止让AI盲目"修复"导致大面积重写 |
| 4. 验证 | VS-3 | 修复后验证安全+验证功能不回退 | 禁止修完不验证 |

**AI代码常见安全问题速查表 (VS-4)**：

| 安全问题 | AI常见错误模式 | 防御策略 |
|---------|---------------|---------|
| SQL注入 | 字符串拼接SQL | 强制参数化查询/ORM |
| XSS | 输出不转义 | 自动转义模板 |
| 硬编码密钥 | API Key/密码直接写在代码中 | 使用环境变量 |
| 缺失鉴权 | 遗漏权限检查 | 标准化中间件 |
| 不安全反序列化 | 使用危险函数 | 白名单类名 |
| 路径遍历 | 未验证文件路径 | 输入验证+白名单 |

### §16.5 出问题禁止重写项目 (第46集)

> 来源：第46集《Vibe Coding出问题就重写项目？错了！》发布约2026-08-07
> 标签：#Vibecoding #AI编程 #小白写代码

**危机处理三原则**：

| 原则 | 铁律 | 内容 | 理由 |
|------|------|------|------|
| 1. 禁止第一反应重写 | VR-1 | 重写是最后手段，不是第一反应 | 重写丢失所有可工作代码和项目知识 |
| 2. 先定位再回退 | VR-2 | 用版本控制定位问题范围→回退到最近可用状态 | git log/diff找到最后的可用commit |
| 3. 增量修复优于全量重写 | VR-3 | 保留可工作代码→增量修复问题区域 | 重写成本几乎总是高于修复成本 |

> **重写决策门槛**：只有当以下条件**全部满足**时才允许重写：
> 1. 问题影响到超过70%的代码模块
> 2. 增量修复已尝试且失败（走完§15四步法）
> 3. 版本控制回退后仍无法工作
> 4. 经§14开发流程A轮讨论通过

### §17.1 心智模型一：不要学AI，直接用 (第1集)

**核心方法论**：以结果为导向的逆向思维

| 传统学习模式 ❌ | Vibe Coding模式 ✅ |

| 追求知识体系完备 | 够用就行，缺啥补啥 |
| 遇到卡壳去查文档/视频 | 直接问AI："这里报错了怎么改？" |

| 角色 | 职责 | 占比 |

### §17.2 心智模型二：最小目标先跑通 (第2集)

**MVP定义三要素**（缺一不可）：

| 要素 | 说明 | 判断标准 |
|------|------|---------|
| **核心价值链路** | 完成用户最核心的1个价值主张 | 用户为这个功能愿意付费/再来 |
| **最短路径** | 去掉所有非必要功能和装饰 | 没有这个功能，产品就不成立 |
| **可验证交付** | 可以独立运行并被用户使用 | 无需依赖后续功能即可体验 |

**版本迭代节奏**：

```text
V0.1 MVP跑通版 (1-2天)
  └── 只做核心链路，页面丑没关系，功能简单没关系
      └── V0.2 功能完善版 (3-5天)
          └── 补齐次要功能，优化交互
              └── V1.0 正式版 (1-2周)
                  └── UI打磨、性能优化、安全加固
```

### §17.4 第一个项目五步法 (第7-8集)

**适用范围**：所有全新启动的Vibe Coding项目，无论大小。

## §18 Prompt工程与上下文管理铁律 (v1.0.0 VIBE-PROMPT-IRON-RULE)

> **⚠️ 硬约束红线**：Prompt是Vibe Coding开发者与AI沟通的唯一语言，Prompt质量决定代码质量。本章节所有Prompt规则为**强制执行**。
> 来源：抖音《Vibe Coding术语》系列 作者：敲代码的小虾米 合集"带你梭哈vibe coding"
> 涵盖集数：第11集(CIRF框架) 第12-15集(结构化Prompt六要素) 第16-18集(上下文窗口管理) 第19集(资产化Prompt库) 第20集(版本化Prompt)
> 规则版本：v18.0.0 新增

### §18.0 核心铁律总表

| 铁律编号 | 来源集 | 铁律内容 | 严重程度 |
|---------|--------|---------|---------|
| **VP-1 (CRITICAL)** | 第11集 | 所有任务级Prompt必须使用**CIRF框架**，禁止自然语言碎碎念 | CRITICAL |

| **VP-3 (CRITICAL)** | 第16-18集 | 单对话上下文占用率**不得超过模型窗口的70%**，超了必须分拆/换新对话 | CRITICAL |

### §18.1 CIRF框架 (第11集)

**CIRF = Context + Instruction + Reference + Format**

| 字母 | 全称 | 说明 | 占比 | 示例 |
|------|------|------|------|------|
| **C** | Context | 背景上下文：告诉AI你是谁、在做什么项目、当前状态 | 30% | "我正在用Flask做一个考试系统的题库模块，当前已建好Question模型" |
| **I** | Instruction | 具体指令：明确要求AI做什么，动作+目标 | 35% | "实现批量导入Excel题库的API，支持单选/多选/判断三种题型" |
| **R** | Reference | 参考材料：代码片段、已有接口规范、错误日志 | 25% | "参考`routes/exam_api.py`第102-150行的出题接口格式" |
| **F** | Format | 输出格式：要求AI如何组织回复内容 | 10% | "先给设计思路，再贴完整代码，最后给调用示例，不要省略代码" |

**CIRF Prompt模板**（可直接复制）：

```
【C-Context】
<项目背景、当前模块、技术栈版本、已完成的部分>

【I-Instruction】
<具体要做什么、验收标准、禁止事项>

【R-Reference】
<相关代码路径/文件、错误截图/日志、已有接口定义>

【F-Format】
<思考过程→代码→使用说明→注意事项 分四段输出>
```

### §18.2 结构化Prompt六要素 (第12-15集)

| 要素 | 说明 | 必要性 | 反例 |
|------|------|:------:|------|
| **① 角色设定** | 设定AI扮演的专家角色 | ✅ 必选 | ❌ 不设定，默认通用助手 |
| **② 任务描述** | 一句话精准描述任务目标 | ✅ 必选 | ❌ "帮我看看这个" |
| **③ 输入数据** | 明确给出AI需要处理的输入 | ✅ 必选 | ❌ 让AI自己猜/找数据 |
| **④ 约束条件** | 列出不能做/必须遵守的限制 | ⚠️ 强烈标准 | ❌ 不写约束，AI自由发挥 |
| **⑤ 输出格式** | 规定输出的结构和粒度 | ⚠️ 强烈标准 | ❌ "你看着办" |
| **⑥ 示例参考** | 给出1-2个正确示例 | 💡 效果倍增 | ❌ 纯抽象描述无示例 |

**合格Prompt vs 不合格Prompt对比**：

| 维度 | ❌ 不合格（碎碎念） | ✅ 合格（六要素齐全） |
|------|-------------------|---------------------|
| 原文 | "那个登录接口好像有问题，你帮我看看呗，改改好吗？昨天还能用的，今天就不行了，真是的..." | 【角色】高级后端工程师<br>【任务】修复登录接口返回500的问题<br>【输入】报错日志见下方，请求体格式`{username,password}`<br>【约束】不能改JWT生成逻辑，保持响应格式兼容<br>【输出】①根因分析 ②修复代码diff ③验证步骤<br>【示例】参考第156号修复单 |
| 结果 | AI大概率问你要日志、问格式、反复确认 | AI一次给出精准修复方案 |

### §18.3 上下文窗口管理 (第16-18集)

#### 模型窗口占用率监控公式

```text
当前占用率 = (已输入Tokens + 预计输出Tokens) / 模型总Tokens上限

安全阈值  : ≤ 50% （绿色，正常工作）
警戒阈值  : 50% ~ 70% （黄色，准备分流）
危险阈值  : > 70% （红色，必须立即处理）
```

#### 上下文瘦身七法（VP-3关联）

| 方法 | 适用场景 | 操作要点 |
|------|---------|---------|
| **① 换新对话法** | 单对话超过15轮 | 新对话+§15.2真源文档四要素 |
| **② 摘要压缩法** | 中间讨论内容冗长 | 让AI："把前面10轮讨论压缩成3句话摘要"，只保留摘要 |
| **③ 文件外移法** | 代码贴了一大堆 | 改为："参考路径`app/services/auth.py`第50-120行" |
| **④ 进一减一法** | 新信息不断进来 | VP-6铁律：加一个新文件上下文→移除一个已完成模块的上下文 |
| **⑤ 模块隔离法** | 多模块并行开发 | 登录模块对话A、题库模块对话B，各司其职不串台 |
| **⑥ 仅保留差异** | 反复迭代同一代码 | 只保留最新版本代码+最新修改需求，删除历史版本diff |
| **⑦ 系统提示冻结** | 通用规则重复出现 | 把开发规则放入IDE系统提示（.trae/rules），不在Prompt中重复 |

#### 上下文三段式前置加载法（VP-7）

```text
第1段 角色注入（固定100Tokens）
  "你是资深全栈工程师，精通Flask+Vue+MySQL，遵循MTSCOS开发规则§1-§18，
   代码输出必须通过§23质量评审。"

第2段 示例注入（固定200Tokens）
  "以下是合格的代码示例：
   [贴1个经过验收的标准代码片段]"

第3段 约束注入（固定150Tokens）
  "禁止事项：不硬编码密钥、不跳过鉴权、不省略错误处理、行宽≤120字符。
   输出必须：先讲思路→再给完整代码→最后给调用方法。"
```

> 三段式前置加载可将单次Prompt有效输出质量提升约40%，重复任务场景必须固化为资产。

### §18.5 版本化Prompt管理 (第20集)

**语义化版本规则**：`MAJOR.MINOR.PATCH`

| 版本位 | 变更类型 | 说明 |
|--------|---------|------|
| **MAJOR** | Prompt骨架变更 | CIRF结构调整、六要素增删、输出格式完全变更 |
| **MINOR** | Prompt内容增强 | 新增约束、补充示例、优化描述表达 |
| **PATCH** | 文字纠错微调 | 错别字、标点、语句润色不影响逻辑 |

**版本管理铁律（VP-5关联）**：

```text
┌──────────────────────────────────────────────────────┐
│ ❌ 禁止：直接在现有VPR_AUTH_001 v1.2.0上覆盖保存        │
│ ✅ 正确：复制为VPR_AUTH_001 v1.3.0 → 修改 → 测试通过   │
│         → 标记v1.2.0为deprecated但保留可回退           │
└──────────────────────────────────────────────────────┘
```

**Prompt A/B测试机制**（高价值场景强制）：

| 测试项 | 方法 |
|--------|------|
| 同任务双版本Prompt并行运行 | v旧 vs v新各生成3次，比较平均质量分 |
| 质量评估维度 | 正确性(40%) / 完整性(30%) / 可用性(30%) |
| 版本晋升标准 | v新平均质量分 ≥ v旧×1.1 且无严重缺陷 |

### §19.3 阶段三：搭骨架 (第25-26集)

**骨架验收六项清单（FS-3关联）**：

| 编号 | 验收项 | 准出标准 | 验证方法 |
|------|--------|---------|---------|
| ① | 目录结构合规 | 完全符合§2.1标准目录布局，根目录仅§2.3.1白名单文件，所有新文件按§2.2.2归档决策树分类 | `tree -L 3` + 根目录文件扫描 |

| ③ | 健康检查接口 | `/health` 返回`{status:healthy}` | 浏览器访问或curl测试 |

### §20.1 测试金字塔规范 (第31-33集)

**金字塔三层比例与投入产出**：

```text
        /_______\       E2E端到端测试  占10%  慢·贵·稳
       /         \      覆盖：关键用户旅程3-5条
      /___________\
     /             \    集成测试     占20%  中·中·用
    /               \   覆盖：API接口+服务间调用
   /_________________\
  /                   \ 单元测试     占70%  快·廉·多
 /_____________________\ 覆盖：Service层/工具函数 核心100%
```

#### 三层测试定义与落地要求

| 层级 | 测试对象 | 示例 | 执行频率 | 通过率要求 |
|------|---------|------|---------|----------|
| **单元测试 (70%)** | 单个函数/类/方法，无外部依赖 | `test_calc_score.py`测判分函数 | 每次提交 | 100%通过 |
| **集成测试 (20%)** | 模块间协作、API接口、DB交互 | `test_exam_api.py`测出题→交卷 | 每天/PR前 | 100%通过 |
| **E2E测试 (10%)** | 真实浏览器端到端模拟用户操作 | 登录→考试→交卷全流程录屏 | 上线前 | 关键链路100% |

**AI写测试Prompt模板**（QT-1关联）：

```
【C】我有一个判分函数位于app/services/scoring.py:50-120，输入学生答案和标准答案，输出分数
【I】为这个函数写完整的单元测试，要求覆盖率≥90%，包含正常/边界/异常场景
【R】参考已有的test_auth.py作为格式样板
【F】遵循AAA模式，每个测试函数名说明：test_<被测场景>_<预期结果>，先给测试清单再写代码
```

**AAA测试命名规范（QT-5关联）**：

```python
# ✅ 好的命名：一眼看懂测什么场景
def test_submit_exam_when_already_submitted_should_raise_400():
    """Arrange: 构造已交卷状态"""
    exam = create_exam(status='submitted')
    """Act: 尝试再次提交"""
    result = submit_exam(exam.id, answers)
    """Assert: 抛出400"""
    assert result.code == 400

# ❌ 坏的命名
def test_exam():
    assert do_something()
```

### §20.2 重构三件套规范 (第34-36集)

**重构定义**：在不改变外部可观测行为的前提下，优化内部代码结构。改功能≠重构。

| 件号 | 名称 | 说明 | 耗时占比 |
|------|------|------|---------|
| **① 读全** | 全量阅读理解 | 读透：调用方图+依赖图+数据流图，搞清楚为什么这么写 | 50% |
| **② 改小** | 最小增量修改 | 一次只改一处，改完立即验证，再改下一处 | 30% |
| **③ 验证** | 测试全量回归 | 老测试100%通过+新增行为测试用例 | 20% |

**重构前检查清单（QT-6关联）**：

| 检查项 | 必须满足 | 不满足时的动作 |
|--------|---------|--------------|
| 老测试存在 | 目标模块有≥3个单元测试 | 先补测试，补完跑通再重构 |
| 老测试通过 | 老测试运行结果100%绿 | 先修老测试Fail项，基线必须是绿的 |
| 调用地图绘完 | 列出所有调用目标代码的位置 | grep/find全项目引用，列出清单 |
| 数据流向清楚 | 输入是什么→过程怎么变→输出到哪儿 | 画数据流图，白纸或AI生成 |
| 不改功能承诺 | 本次重构不改接口不改行为 | 白纸黑字写在PR描述第1条 |

**重构反模式（严禁）**：

```text
❌ 大爆炸重构：一次改20个文件，删500行加500行
❌ 顺手改：重构A的时候顺便把B也改了
❌ 改名党：把user改成account，改完全项目替换，其他啥都没变
❌ 先拆后跑：拆了一堆文件，跑不起来，三天三夜才合回去
```

### §20.3 版本分支策略 (第37-38集)

**Git Flow极简版（QT-3关联）**：

```text
main (生产分支，保护分支，禁止直推)
  ↑  merge by PR
develop (集成分支，保护分支)
  ↑  merge by PR
feature/xxx (功能分支，从develop切出)
  │   命名：feature/模块-功能描述
  │   示例：feature/exam-batch-import
  └──→ 开发完→PR回develop

hotfix/xxx (紧急修复，从main切出)
  │   命名：hotfix/bug-描述
  │   示例：hotfix/login-token-expire
  └──→ 修复完→PR同时回main和develop
```

**五条分支铁律**：

| 编号 | 铁律 | 违反后果 |
|------|------|---------|
| BF-1 | 禁止`git push origin main`直推 | main保护分支+pre-push hook双拦截 |
| BF-2 | 功能从`develop`切，修完回`develop` | 切错分支直接打回重开PR |
| BF-3 | `feature/`分支生命≤7天 | 超时未合并自动告警，超14天自动作废 |
| BF-4 | 一个分支一个主题，禁止多混 | "加出题+改登录+修样式"拆开成3个分支 |
| BF-5 | 合并前`rebase develop`，禁止冲突合并 | PR有Conflict直接打回，不处理冲突 |

### §20.4 PR七步法规范 (第39-40集)

**PR = Pull Request，代码合并请求。所有合并必须走PR，禁止本地merge后push。**

| 步骤 | 名称 | 交付物/动作 | 检查要点 |
|------|------|------------|---------|
| **① 填模板** | 填写PR标准模板 | 标题按`<类型>(<范围>): <描述>` | 关联Issue/需求号必填 |
| **② 贴截图** | Before/After对比 | UI改动截图，接口改动Postman截图 | 无图无真相，无图直接打回 |
| **③ 跑测试** | 本地跑完全部测试 | `pytest`全绿+覆盖率报告截图 | 有红不让提PR |
| **④ 跑lint** | 代码规范检查 | `flake8`/`eslint`零error | 有error不让提PR |
| **⑤ 写变更** | 列出本次变更清单 | 按文件/模块列"改了什么" | 评审人5秒看懂改了啥 |
| **⑥ 自测单** | 测试要点列表+结果 | 每个改动点怎么测的/结果 | `☑ 登录成功 ☑ 403拦截生效` |
| **⑦ 指定人** | 指定评审人+关联合规 | 至少1人Review，重要改动≥2人 | 24小时未评审自动催办 |

**PR标准模板（强制）**：

### §22.1 Codex多Agent并行 (第1集 · AC-1关联)

**可并行任务判断三条件（同时满足=可并行）**：

| 条件 | 说明 | 可并行 ✅ | 不可并行 ❌ |
|------|------|---------|-----------|
| **无依赖关系** | A的输出≠B的输入 | "写3个独立页面的模板" | "先建表→再写接口→再写前端"（有先后） |
| **无资源竞争** | 不同时改同一个文件/表/锁 | "测试用例+README+部署脚本" | "同时改同一个routes.py的第50-100行" |
| **上下文不交叉** | 所需背景知识完全可拆分 | "登录模块+支付模块+上传模块" | "修改同一算法的不同参数方案" |

**并行度公式（AC-5关联）**：

```text
最大并行度 = min(
    CPU核心数 × 2,           # 本机算力约束
    LLM模型 RPM/TPM限额 ÷ 单次任务消耗,   # 模型限流约束
    可并行任务总数            # 任务量约束
)

示例：8核CPU + GPT-4o 限额 500RPM/日 + 可拆任务20个
→ min(16, ~30, 20) = 16 个Agent并行
```

**并行任务拆分模板**：

```text
父任务：V0.1版本功能实现
  ├── Agent1 负责：登录模块(1-5号路由+页面)  输出路径：routes/auth + templates/auth
  ├── Agent2 负责：题库模块(6-12号路由+页面) 输出路径：routes/question + templates/question
  ├── Agent3 负责：考试模块(13-20号路由+页面) 输出路径：routes/exam + templates/exam
  └── Agent4 负责：公共组件(Header/Sidebar/Footer/Toast) 输出路径：components/
  （4个并行，互不依赖，输出路径不交叉 ✅）
```

### §22.2 子代理委派规范 (第2集 · AC-2关联)

**委派与自治边界**：

```text
┌────────────────────────────────────────────────────┐
│  父代理（你 / 主AI Agent）                            │
│    ✅ 有权决定：做不做、做什么、技术选型、验收标准        │
│    ❌ 不做的事：逐行写代码、调细节、重复体力活            │
│                    ↓ 下发《委派单》                   │
│  子代理A / 子代理B / 子代理C                          │
│    ✅ 有权决定：实现细节、代码写法、工具选择             │
│    ❌ 不能改的：目标、输入格式、输出格式、约束条件        │
│                    ↓ 交付结果物                       │
│  父代理：验收 + 整合 + 反馈                            │
└────────────────────────────────────────────────────┘
```

**《委派单》四要素模板（AC-6关联）**：

```markdown
## 📋 子代理委派单：Agent-考试接口开发
### ① 目标（做什么，不能改）
完成`POST /api/exams/submit`接口：学生提交答案→判分→保存成绩→返回结果

### ② 输入（给什么材料）
- 参考代码：`app/routes/exam_api.py` 已写好的出题接口（Line 45-90）
- 数据模型：`app/models/exam.py` Exam / ExamQuestion / StudentAnswer
- 判分逻辑文档：`docs/scoring_logic.md`

### ③ 约束（不能做什么，红线）
- ❶ 禁止修改JWT鉴权中间件
- ❷ 禁止修改Question模型字段
- ❸ 判分响应时间≤2秒，超时报错但不中断
- ❹ 必须用`@require_login`装饰器

### ④ 验收（怎么算做完）
- [ ] 正常提交：答案完整→返回score=xx+明细
- [ ] 重复提交：同一学生同一考试第二次提交返回400"已交卷"
- [ ] 权限测试：未登录提交→401跳登录
- [ ] 性能测试：100题判分≤1.5秒
```

> **铁律AC-2执行**：子代理擅自改动①③项的，父代理直接驳回，要求重做。造成损失的，子代理对话作废重开。

### §22.3 批量任务调度规范 (第3集 · AC-3关联)

**批量调度三阶段流水线**：

```text
  阶段1：分组     阶段2：流水     阶段3：收尾
  ┌────────┐   ┌───────────┐   ┌──────────┐
  │ 任务池  │ → │ 并发组A执行│ → │  整合验收  │
  │ 20个任务│   │ 并发组B执行│   │  异常重试  │
  │ 按依赖  │   │ 并发组C执行│   │  汇总报告  │
  │ 分4组  │   │ (并度=3)  │   │          │
  └────────┘   └───────────┘   └──────────┘
```

### §22.4 上下文隔离规范 (第4集 · AC-4关联)

**污染案例（为什么必须隔离）**：

```text
❌ 不隔离导致的灾难：
  Agent-A修支付Bug，对话中贴了"把price字段改成decimal(12,4)"
  → Agent-B做商品列表，AI"记住了"刚才的上下文
  → 偷偷把varchar的product_name也改成了decimal(12,4)
  → 上线后商品名称全变0.0000 💥
```

**四级隔离机制**：

| 级别 | 隔离手段 | 防止的污染 | 适用场景 |
|------|---------|----------|---------|
| **L1 对话隔离** | 每个Agent一个独立对话窗口/线程 | 历史消息串味 | 所有多Agent场景必选 |
| **L2 工作目录隔离** | 每个Agent一个独立`workspace/agent_xxx/`临时目录 | 中间文件互相覆盖 | 有文件生成任务 |
| **L3 Git分支隔离** | 每个Agent一个独立`feature/agent-xxx`分支 | 同文件并发编辑冲突 | 大型并行开发 |
| **L4 提示词冻结隔离** | 系统提示词写死"你只负责XX模块，禁止触碰其他" | 越权修改其他模块代码 | 高风险场景/子代理委派 |

**隔离落库监控**：

| 监控项 | 阈值 | 触发动作 |
|--------|------|---------|
| Agent读取非本模块文件 | ≥1次 | 告警+阻断（L4未启用时） |
| Agent修改委派约束中禁止的内容 | ≥1次 | 自动回滚+对话作废 |
| 对话交叉引用其他Agent上下文 | Token占比>10% | 警告+强制新对话 |

### §22.5 数据库落库规范

| 表名 | 用途 | 关键字段 |
|------|------|---------|

| `mt_vibe_agent_task` | 单个Agent任务 | batch_id, task_id, group_no, assigned_agent, status, retry_no, timeout_sec, input_payload, output_result |

## 17. Vibe Coding思维模式 (VC-T 思维铁律)

> **开发规则 §17 · IR级铁律** · 来源：抖音Vibe Coding带你梭哈1-40集思维篇

### 17.1 AI协作核心思维

| 思维模式 | 说明 | 铁律编号 |
|----------|------|----------|
| **分治思维** | 大问题拆解为可独立验证的小问题，一口一口吃大象 | VC-T1 (CRITICAL) |
| **迭代思维** | MVP→反馈→优化→反馈，快速小步快跑而非一步到位 | VC-T2 (CRITICAL) |
| **验证思维** | 每一步可验证、可回滚、可观测，拒绝写完再测 | VC-T3 (HIGH) |
| **上下文管理** | 给AI的上下文精准结构化，信息冗余与不足双避 | VC-T4 (HIGH) |
| **人机分工** | AI做广度/搜索/模板/格式化，人做深度/决策/审美/架构 | VC-T5 (HIGH) |

### 17.2 分治思维实操 (VC-T1)
**四步拆解法：**
1. **需求拆解**：目标→约束→边界→验收标准 写清楚
2. **架构拆解**：模块→接口→数据流→依赖关系 画出来
3. **实现拆解**：文件→函数→类→行级任务 分清单
4. **验证拆解**：单测→集成→E2E→性能→安全 全覆盖

**禁止：** 一个Prompt让AI实现完整系统（超过500行/5个文件的需求必须拆解）

### 17.3 迭代思维实操 (VC-T2)
**Vibe Coding迭代节奏：**
```
Cycle 1 (Day 1):    核心骨架跑通 - 能跑就行
Cycle 2 (Day 2-3):  功能补全完善 - 边界+错误处理
Cycle 3 (Day 4-5):  优化打磨提升 - 性能+体验+代码质量
Cycle 4 (Day 6):    测试+评审+文档 - 正式交付
```
**每个Cycle输出必须：** 可运行 + 可演示 + 可回滚

### 17.4 验证思维实操 (VC-T3)
- **代码写完立即测**：不攒代码库，50-100行一个验证点
- **控制台无报错**：开发模式下DevTools Console 0 Error是底线
- **断言式开发**：先写期望结果Assert，再写实现代码
- **可视化验证**：UI组件必须截图比对回归，前后对照存档

## 18. Vibe Coding Prompt工程 (VC-Prompt 铁律)

> **开发规则 §18 · IR级铁律** · 来源：抖音Vibe Coding术语课+Prompt专项+带你梭哈系列

### 18.1 Prompt结构化五要素 (CRITICAL)

| 要素 | 说明 | 铁律编号 |
|------|------|----------|
| **角色(Role)** | 明确AI扮演的专家角色+经验年限+擅长领域 | VC-P1 (CRITICAL) |
| **任务(Task)** | 具体要做什么，输入/输出/边界/约束明确 | VC-P2 (CRITICAL) |
| **上下文(Context)** | 项目背景/技术栈/现有代码/规范文档引用 | VC-P3 (HIGH) |
| **示例(Example)** | 1-3个输入输出示例，零样本→少样本→多样本 | VC-P4 (HIGH) |
| **格式(Format)** | 输出格式严格约束：JSON/Markdown/代码块/列表 | VC-P5 (CRITICAL) |

### 18.2 代码生成Prompt模板 (VC-P2/5)

```markdown

- 禁止事项：{LIST_OF_DONT}
- 必须使用：{LIST_OF_MUST_USE}
- 代码风格：匹配{EXISTING_CODE_STYLE_REF}

# 上下文

- 现有相关代码：
```

```
- 数据结构：
```

```

### 18.3 上下文管理铁律 (VC-P3)
- **黄金窗口**：单次Prompt上下文长度控制在模型窗口的30-70%
- **信息分层**：核心约束放最前 → 代码片段中间 → 背景说明最后
- **精准引用**：引用规则文件必须标章节号，引用代码必须给文件:行号
- **上下文压缩**：长对话定期归档总结，用摘要代替完整历史

### 18.4 Prompt反模式黑名单 (VC-P2/5)
| 反模式 | 危害 | 修正方案 |
|--------|------|----------|
| "帮我写个系统" | 范围失控，质量不可控 | 按VC-T1分治，拆成10+个小Prompt |
| 无约束自由发挥 | 偏离项目规范/技术栈 | 强制列出约束清单+禁止清单 |
| 只说功能不说格式 | 输出不可解析，难自动化 | 严格JSON Schema或格式约束 |
| 复制粘贴整个文件 | 上下文爆炸+注意力分散 | 只给相关函数/类+文件路径引用 |

## 19. Vibe Coding全栈开发 (VC-FS 全栈铁律)

> **开发规则 §19 · IR级铁律** · 来源：抖音Vibe Coding带你梭哈全栈篇+技术栈拆解11集

### 19.1 全栈架构分层原则

| 层级 | 职责 | 铁律编号 |
|------|------|----------|
| **表现层(Frontend)** | UI渲染/交互/状态管理/路由/表单验证 | VC-FS1 (CRITICAL) |
| **接口层(API Gateway)** | 路由转发/鉴权/限流/日志/熔断 | VC-FS2 (HIGH) |
| **业务层(Service)** | 核心业务逻辑/领域模型/事务/校验 | VC-FS3 (CRITICAL) |
| **数据层(DAO/Repository)** | DB访问/缓存/ORM/查询优化 | VC-FS4 (HIGH) |
| **基础设施(Infra)** | 部署/监控/CI-CD/存储/消息队列 | VC-FS5 (MEDIUM) |

**铁律 VC-FS1/3：禁止跨层调用** — 表现层绝不直连DB，必须经Service；Service绝不操作DOM。

### 19.2 API设计RESTful+规范 (VC-FS2)

**URL命名：**
```
✅ GET    /api/v1/users              # 列表
✅ GET    /api/v1/users/:id          # 详情
✅ POST   /api/v1/users              # 创建
✅ PUT    /api/v1/users/:id          # 全量更新
✅ PATCH  /api/v1/users/:id          # 部分更新
✅ DELETE /api/v1/users/:id          # 删除
✅ POST   /api/v1/users/:id/activate # 动作：激活
❌ /api/v1/getUserList  /api/v1/userCreate  /api/v1/users-delete-all
```

**统一响应结构：**
```json
{
  "code": 0,
  "message": "success",
  "data": { },
  "request_id": "uuid-trace-id",
  "timestamp": 1700000000000
}
```
code=0成功，非0错误码按模块分段：1xxx通用/2xxx认证/3xxx权限/4xxx参数/5xxx业务/6xxx服务端

### 19.3 数据流转铁律 (VC-FS4)
- **请求链路**：Frontend → DTO(请求) → Service校验 → Entity → DAO → DB
- **响应链路**：DB → DAO → Entity → Service → DTO(响应) → Frontend
- **禁止**：Entity直接出参（必须DTO转换，隔离内部字段）
- **缓存策略**：热点读数据Redis缓存，DB写操作立即失效对应缓存

### 19.4 前后端协作契约 (VC-FS1/2/3)
- API优先：先定OpenAPI/Swagger契约文档，再各自并行开发
- Mock服务：前端开发期间使用Mock Server，不阻塞等待后端
- 接口变更：API变更必须走变更流程+版本号递增+兼容期至少2个版本
- 联调流程：单模块联调 → 集成联调 → 预发布联调 → 生产灰度

## 20. Vibe Coding质量保障 (VC-QA 质量铁律)

> **开发规则 §20 · IR级铁律** · 来源：抖音Vibe Coding实用技巧4集+带你梭哈质量篇

### 20.1 测试金字塔全覆盖

| 测试类型 | 占比 | 执行时机 | 通过率要求 | 铁律编号 |
|----------|------|----------|------------|----------|
| **单元测试 Unit** | 70% | 每次commit触发CI | 100% (新增) ≥90% (全量) | VC-Q1 (CRITICAL) |
| **集成测试 Integration** | 20% | PR/MR时CI触发 | 100% | VC-Q2 (HIGH) |
| **E2E端到端测试** | 8% | 每日Nightly + 发布前 | 100% (核心路径) ≥95% (全) | VC-Q3 (HIGH) |
| **性能测试 Performance** | 1.5% | 每周 + 大版本前 | 满足性能预算不退化 | VC-Q4 (MEDIUM) |
| **安全测试 Security** | 0.5% | 每周SAST + 发布前DAST | 0 Critical / 0 High | VC-Q5 (CRITICAL) |

### 20.2 单元测试铁律 (VC-Q1)
- **AAA模式**：Arrange(准备) → Act(执行) → Assert(断言) 三段式
- **Given-When-Then**：BDD风格描述测试case，可读性优先
- **Mock边界**：外部依赖(DB/HTTP/时间/随机)必须Mock，纯函数不Mock
- **覆盖标准**：
  - 语句覆盖 ≥ 90%
  - 分支覆盖 ≥ 85%
  - 关键路径覆盖 100%

### 20.3 1000轮测试强制规范 (VC-Q2/3)
测试三大场景比例必须：
```
NORMAL_LOGIC 正常场景:  40% → 验证正向逻辑全部正确
ABNORMAL_LOGIC 异常场景: 30% → 验证错误处理/边界条件/非法输入
HACKER_ATTACK 黑客场景: 30% → 验证注入/越权/绕过/破坏式攻击
```
**测试结果评级：**
| 通过率 | 漏洞数 | 评级 | 结论 |
|--------|--------|------|------|
| 100% | 0 | **S** | 完美交付，可上线 |
| ≥99% | ≤1 | A | 修复后可上线 |
| ≥95% | ≤3 | B | 修复后回归通过 |
| ≥90% | ≤5 | C | 需要大面积修复 |
| <90% | >5 | D | 不通过，打回重做 |

### 20.4 代码质量静态检查 (VC-Q1/2)
- **Linter**：ESLint + Pylint + Ruff 全量开启
- **Formatter**：Prettier + Black 统一风格，CI强校验不通过不合并
- **Type Check**：TypeScript strict mode + Pyright 严格模式
- **复杂度**：圈复杂度 ≤ 10 / 函数行数 ≤ 50 / 文件行数 ≤ 500

### 20.5 发布前质量门禁 (VC-Q3/4/5)
发布火车必须同时满足：
1. ✅ 全部测试通过率100%（Unit+Integration+E2E核心）
2. ✅ 0 Critical / 0 High 安全漏洞
3. ✅ 性能指标不低于上一版本5%以上
4. ✅ Lint/Format/Type 0 Error
5. ✅ 代码评审Approve + 变更文档齐全
6. ✅ 回滚方案验证可用（生产15分钟内可回滚）

### 21.2 技术栈变更流程 (VC-TS1/2/6/7)

## 23. Vibe Coding代码评审 (VC-CR 评审铁律)

> **开发规则 §23 · IR级铁律** · 来源：抖音Vibe Coding带你梭哈评审篇+作品评审1集

### 23.1 评审十维检查清单 (必须逐项打勾)

| 维度 | 检查项 | 铁律编号 |
|------|--------|----------|
| **正确性** | 功能实现是否符合需求？边界/异常是否正确处理？ | VC-CR1 (CRITICAL) |
| **规范合规** | 是否符合设计规范+开发规则？有没有VC-*铁律违反？ | VC-CR2 (CRITICAL) |
| **代码质量** | 命名清晰？函数/文件大小？圈复杂度？DRY原则？ | VC-CR3 (HIGH) |
| **性能** | N+1查询？大循环？不必要的重渲染？是否在性能预算内？ | VC-CR4 (HIGH) |
| **安全** | 输入校验？XSS/SQL注入？鉴权越权？敏感数据泄露？ | VC-CR5 (CRITICAL) |
| **可测试性** | 依赖是否可Mock？是否有对应单测？覆盖是否达标？ | VC-CR6 (HIGH) |
| **可维护性** | 注释是否充分Why？是否有技术债标记TODO？命名是否达意？ | VC-CR7 (MEDIUM) |
| **兼容性** | 前后端接口兼容？旧版本数据兼容？浏览器/设备兼容？ | VC-CR8 (HIGH) |
| **文档变更** | README/API/内联注释是否同步变更？CHANGELOG是否更新？ | VC-CR9 (MEDIUM) |
| **用户体验** | 交互是否符合设计规范？错误提示是否友好？加载态/空态是否处理？ | VC-CR10 (MEDIUM) |

### 23.2 评审分级与SLA

| 变更类型 | 评审人 | 评审SLA | Approve要求 |
|----------|--------|---------|-------------|
| **Tiny** (≤50行,文档/配置/文案) | 同模块任意开发 | 4小时 | 1 Approve |
| **Small** (≤200行,小功能/Bugfix) | 模块Owner+1名资深 | 1工作日 | 2 Approve |
| **Medium** (≤500行,中功能/重构) | 模块Owner+架构师 | 2工作日 | 2+1(SA可选) Approve |
| **Large** (>500行,大模块/架构级) | 拆分后逐PR评审 + SA终评 | 拆分后逐个 | SA必须Approve |

### 23.3 Review评论分类标准
- **Blocking (必须改)**：正确性/安全/规范合规类问题，不改不能合入
- **Major (强烈必须)**：性能/代码质量/可测试性类问题，必须修后合入
- **Minor (必须)**：可维护性/命名/注释优化类，可下次迭代修
- **Nit (吐槽/偏好)**：纯个人偏好类，仅参考不强制
- **Question (疑问)**：不确定/需要讨论/需要更多上下文的点

### 23.4 作品评审专项标准 (针对Vibe Coding作品评审1集)
Vibe Coding体系对外作品（分享/案例/教程/开源项目）额外评审：
1. ✅ 术语准确度：VC-*术语使用是否精准，与体系一致？
2. ✅ 方法论可复现性：步骤是否清晰，他人按步骤能否复现同样结果？
3. ✅ 最佳实践标注：哪些是通用最佳实践，哪些是项目特定选择？
4. ✅ 踩坑经验记录：真实踩坑+解决方案，而非完美无暇"假教程"
5. ✅ 可扩展空间：方法是否可扩展？进阶方向指引是否明确？
