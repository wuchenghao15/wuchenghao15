# MTSCOS AI 项目源码修改准则参考与思路方案

## 1. 总则

### 1.1 目的

为规范MTSCOS AI项目源码修改流程，确保AI修改源码的质量、安全性和一致性，统一修改与拓展方向，特制定本准则。

### 1.2 适用范围

本准则适用于MTSCOS AI项目中所有源码修改活动，包括：
- AI自动修改源码
- 人工修改源码
- 代码重构
- 功能扩展
- Bug修复
- 性能优化

### 1.3 核心原则

| 原则 | 说明 |
|------|------|
| **安全优先** | 任何修改必须确保系统稳定性和数据安全 |
| **一致性** | 修改必须与现有代码风格、架构和规范保持一致 |
| **可追溯** | 所有修改必须有完整的记录和日志 |
| **可测试** | 修改必须有对应的测试用例验证 |
| **渐进式** | 大的修改必须分阶段进行，避免一次性引入大量变更 |
| **审查机制** | 所有修改必须经过代码审查 |
| **巡检驱动** | 修改后必须通过AI巡检引擎检查，支持自动修复 |
| **法律准则合规** | 所有修改必须遵循法律准则文件规定 |
| **自动修复闭环** | 发现问题自动触发修复流程，修复结果记录到数据库并投喂脑库 |

## 2. 源码修改流程规范

### 2.1 修改流程总览

```
需求分析 → 方案设计 → 分支创建 → 代码修改 → 测试验证 → 代码审查 → 合并部署
                    ↓
              风险评估
```

### 2.2 各阶段规范

#### 2.2.1 需求分析阶段

| 规范项 | 要求 |
|--------|------|
| 需求文档 | 必须有明确的需求文档或Issue描述 |
| 影响范围分析 | 必须分析修改对系统的影响范围 |
| 依赖分析 | 必须分析相关依赖和冲突风险 |
| 优先级评估 | 必须评估修改的优先级和紧急程度 |

#### 2.2.2 方案设计阶段

| 规范项 | 要求 |
|--------|------|
| 技术方案 | 必须提供详细的技术方案文档 |
| 架构一致性 | 方案必须与现有架构保持一致 |
| 可扩展性 | 方案必须考虑未来扩展需求 |
| 回滚方案 | 必须提供回滚方案和应急预案 |

#### 2.2.3 风险评估

| 风险类型 | 评估内容 | 应对措施 |
|---------|---------|---------|
| **功能风险** | 修改是否会影响现有功能 | 编写回归测试 |
| **性能风险** | 修改是否会影响系统性能 | 性能测试验证 |
| **安全风险** | 修改是否引入安全漏洞 | 安全审查 |
| **兼容性风险** | 修改是否破坏向后兼容 | 兼容性测试 |
| **数据风险** | 修改是否影响数据一致性 | 数据备份和迁移方案 |

## 3. 代码风格规范

### 3.1 Python代码风格

#### 3.1.1 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 模块名 | 小写，下划线分隔 | `auth_service.py` |
| 类名 | 大驼峰 | `AuthService` |
| 方法名 | 小写，下划线分隔 | `get_user_by_id()` |
| 变量名 | 小写，下划线分隔 | `user_id` |
| 常量名 | 全大写，下划线分隔 | `MAX_RETRY_COUNT` |
| 蓝图名 | 小写，下划线分隔 | `admin_api` |

#### 3.1.2 代码风格规则

| 规则 | 要求 |
|------|------|
| 缩进 | 使用4空格（禁止使用Tab） |
| 行宽 | 不超过120字符 |
| 语句 | 每行一个语句，禁止多语句同行 |
| 类型提示 | 必须使用Type Hints |
| 文档字符串 | 模块级函数和类必须有Docstring |

#### 3.1.3 导入规范

```python
# 标准库导入（按字母顺序）
import os
import re
from datetime import datetime

# 第三方库导入（按字母顺序）
from flask import Flask, jsonify
from sqlalchemy import create_engine

# 项目内部导入（按字母顺序）
from app.models.user import User
from app.services.auth_service import AuthService
```

### 3.2 JavaScript代码风格

#### 3.2.1 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 文件名 | 小写，下划线分隔 | `theme_manager.js` |
| 变量名 | 小驼峰 | `userInfo` |
| 函数名 | 小驼峰 | `getUserInfo()` |
| 类名 | 大驼峰 | `ThemeManager` |
| 常量名 | 全大写，下划线分隔 | `API_BASE_URL` |

### 3.3 前端模板规范

| 规则 | 要求 |
|------|------|
| 模板继承 | 必须使用Jinja2模板继承 |
| CSS引入 | 必须按顺序引入设计系统CSS |
| 禁止事项 | 禁止硬编码颜色值、禁止内联样式、禁止外部CDN |

## 4. 分支管理策略

### 4.1 分支类型

| 分支 | 用途 | 命名规范 |
|------|------|---------|
| `main` | 主分支，生产环境代码 | 固定名称 |
| `develop` | 开发分支，集成所有功能 | 固定名称 |
| `feature/xxx` | 功能分支，开发新功能 | `feature/模块名-功能名` |
| `bugfix/xxx` | Bug修复分支 | `bugfix/模块名-问题描述` |
| `hotfix/xxx` | 紧急修复分支 | `hotfix/模块名-问题描述` |
| `refactor/xxx` | 代码重构分支 | `refactor/模块名-重构内容` |

### 4.2 分支生命周期

| 分支类型 | 创建来源 | 合并目标 | 删除时机 |
|---------|---------|---------|---------|
| `feature/xxx` | `develop` | `develop` | 合并后删除 |
| `bugfix/xxx` | `develop` | `develop` | 合并后删除 |
| `hotfix/xxx` | `main` | `main` + `develop` | 合并后删除 |
| `refactor/xxx` | `develop` | `develop` | 合并后删除 |

### 4.3 AI修改分支规范

| 规范项 | 要求 |
|--------|------|
| 分支命名 | `feature/ai-模块名-功能描述` |
| 修改范围 | 单个分支只包含一个功能的修改 |
| 提交频率 | 每个小功能完成后立即提交 |
| 冲突处理 | 定期同步develop分支，及时处理冲突 |

## 5. 提交信息规范

### 5.1 提交信息格式

```
<类型>(<范围>): <描述>

<详细说明>

<关联信息>
```

### 5.2 提交类型

| 类型 | 说明 | 适用场景 |
|------|------|---------|
| `feat` | 新功能 | 添加新功能、新模块 |
| `fix` | Bug修复 | 修复已知问题 |
| `docs` | 文档更新 | 更新文档、注释 |
| `style` | 样式修改 | 代码格式调整、样式更新 |
| `refactor` | 代码重构 | 代码重构、优化结构 |
| `test` | 测试代码 | 添加或修改测试 |
| `chore` | 构建/工具更新 | 构建脚本、依赖更新 |
| `perf` | 性能优化 | 性能改进、优化算法 |
| `revert` | 回滚 | 回滚之前的提交 |

### 5.3 提交范围

| 范围 | 说明 | 示例 |
|------|------|------|
| `auth` | 认证模块 | `feat(auth): 添加OAuth2登录` |
| `exam` | 考试模块 | `fix(exam): 修复试卷生成问题` |
| `question` | 题库模块 | `refactor(question): 优化题目查询` |
| `admin` | 管理后台 | `style(admin): 更新管理员界面` |
| `ai` | AI引擎 | `feat(ai): 添加智能推荐引擎` |
| `api` | API接口 | `fix(api): 修复用户信息接口` |

### 5.4 提交信息示例

```
feat(question): 添加专项竞赛题库生成功能

- 实现数学竞赛题目生成器
- 添加物理竞赛题库模板
- 支持自定义竞赛类型配置

关联Issue: #123
```

### 5.5 AI提交规范

| 规范项 | 要求 |
|--------|------|
| 描述清晰 | 提交信息必须清晰描述修改内容 |
| 详细说明 | 复杂修改必须提供详细说明 |
| 关联信息 | 必须关联相关Issue或需求文档 |
| 提交粒度 | 每次提交只包含一个逻辑单元 |

## 6. 测试要求规范

### 6.1 测试类型

| 测试类型 | 说明 | 覆盖率要求 |
|---------|------|-----------|
| **单元测试** | 测试单个函数或方法 | ≥80% |
| **集成测试** | 测试模块间交互 | ≥60% |
| **API测试** | 测试API接口 | 全部接口 |
| **回归测试** | 测试现有功能不受影响 | 全部核心功能 |
| **性能测试** | 测试系统性能 | 满足性能指标 |

### 6.2 测试文件结构

```
tests/
├── __init__.py
├── conftest.py           # 测试配置和fixture
├── test_auth.py          # 认证模块测试
├── test_exam.py          # 考试模块测试
├── test_api.py           # API接口测试
├── test_services/        # 服务层测试
│   ├── __init__.py
│   ├── test_course_service.py
│   └── test_exam_service.py
├── test_models/          # 模型层测试
│   ├── __init__.py
│   └── test_user_model.py
└── test_agents/          # Agent测试
    ├── __init__.py
    └── test_approval_manager.py
```

### 6.3 测试执行规范

| 命令 | 用途 |
|------|------|
| `python -m pytest` | 运行所有测试 |
| `python -m pytest tests/test_auth.py` | 运行特定测试 |
| `python -m pytest tests/test_services/` | 运行服务层测试 |
| `python -m pytest --cov=app --cov-report=html` | 生成测试覆盖率报告 |

### 6.4 AI修改测试规范

| 规范项 | 要求 |
|--------|------|
| 新增测试 | 新增功能必须添加对应测试用例 |
| 回归测试 | 修改必须运行回归测试确保不破坏现有功能 |
| 测试通过 | 所有测试必须通过才能提交 |
| 覆盖率 | 新增代码测试覆盖率必须≥80% |

## 7. 代码审查流程规范

### 7.1 审查流程

```
提交PR → CI自动检查 → 代码审查 → 审查通过 → 合并
            ↓
       测试失败？
          ↓
     是 → 修复后重新提交
```

### 7.2 审查标准

| 审查项 | 标准 |
|--------|------|
| **代码风格** | 符合项目代码规范 |
| **架构一致性** | 与现有架构保持一致 |
| **安全性** | 无安全漏洞 |
| **性能** | 无性能问题 |
| **可测试性** | 代码易于测试 |
| **文档** | 有完整的文档和注释 |
| **测试覆盖** | 测试用例完整 |

### 7.3 AI修改审查规范

| 规范项 | 要求 |
|--------|------|
| 审查人 | 必须有至少一名人工审查人 |
| 审查内容 | 必须审查AI生成代码的正确性和安全性 |
| 审查记录 | 审查结果必须记录到数据库 |
| 审查时间 | 紧急修改24小时内完成审查，普通修改48小时内 |

## 8. AI修改源码方案参考

### 8.1 AI修改策略

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| **QUICK_FIX** | 快速修复，最小改动 | Bug修复、紧急问题 |
| **DEEP_FIX** | 深度修复，重构相关代码 | 复杂Bug、架构问题 |
| **MULTI_FIX** | 多项修复，同时解决多个问题 | 相关问题批量修复 |
| **COLLABORATIVE_FIX** | 协作修复，AI与人工共同完成 | 关键功能、安全问题 |
| **AUTOMATIC_FIX** | 自动修复，AI独立完成 | 简单问题、重复性任务 |
| **MANUAL_FIX** | 人工修复，AI提供建议 | 复杂问题、架构决策 |

### 8.2 AI修改流程

```
问题识别 → 方案生成 → 代码修改 → 测试验证 → 审查提交

```

| 规范项 | 要求 |
|--------|------|
| 多种方案 | 必须提供至少2种解决方案 |
| 方案对比 | 必须对比各方案优缺点 |

#### 8.2.3 代码修改阶段

| 规范项 | 要求 |

## 10. 版本管理规范

### 10.1 版本号规则

遵循SemVer标准（X.Y.Z）：

| 版本号 | 含义 | 更新条件 |
|--------|------|---------|
| **Major** (X) | 主版本号 | 不兼容的API变更 |
| **Minor** (Y) | 次版本号 | 新增功能，向后兼容 |
| **Patch** (Z) | 修订号 | Bug修复，向后兼容 |

### 10.2 版本更新触发条件

| 条件 | 触发更新 |
|------|---------|
| 代码变更≥10 | Minor更新 |
| 安全补丁≥1 | Patch更新 |
| 新增功能≥1 | Minor更新 |
| Bug修复≥5 | Patch更新 |
| 性能优化≥3 | Patch更新 |
| 依赖更新≥3 | Patch更新 |
| 距上次发布≥30天 | Patch更新 |
| 用户反馈≥50 | Minor更新 |

### 10.3 版本更新流程

```
代码修改 → 测试通过 → 版本号更新 → 变更日志 → 健康检查 → 发布
```

### 10.4 版本违规处罚

| 违规类型 | 级别 | 处罚 |
|---------|------|------|
| 版本格式错误 | ERROR | 3次禁用自动更新 |
| 版本号递减 | CRITICAL | 2次锁定系统 |
| 缺少变更日志 | WARNING | 5次警告 |
| 未备份更新 | ERROR | 3次阻止更新 |
| 更新失败 | WARNING | 10次禁用自动更新 |
| 健康检查失败 | ERROR | 5次触发回滚 |

## 12. AI自动修复流程规范

### 12.1 自动修复触发条件

| 触发条件 | 说明 | 优先级 |
|---------|------|-------|
| 语法错误检测 | AI巡检引擎检测到Python/JS/HTML/CSS/JSON语法错误 | 高 |

| 代码质量扫描 | 巡检引擎扫描发现的代码质量问题 | 中 |
| 手动触发修复 | 管理员手动触发的修复任务 | 高 |

### 12.2 自动修复流程

```
1. 错误检测（语法检查/运行时错误/代码扫描）
2. 错误分类（语法错误/代码质量/安全问题/合规问题）
3. 方案生成（从脑库匹配或AI生成修复方案）
4. 置信度评估（评估修复方案置信度）
5. 代码备份（修复前备份原始代码）
6. 执行修复（应用修复代码）
7. 验证修复（验证修复后代码正确性）
8. 记录日志（记录修复详情到数据库）
9. AI学习（将成功修复经验写入脑库）
10. 通知告警（发送修复结果通知）
```

### 12.3 自动修复策略

| 策略 | 说明 | 适用场景 | 置信度门槛 |
|------|------|---------|-----------|
| QUICK_FIX | 快速修复，最小改动 | 简单语法错误 | ≥0.9 |
| DEEP_FIX | 深度修复，重构相关代码 | 复杂Bug、架构问题 | ≥0.8 |
| MULTI_FIX | 多项修复，同时解决多个问题 | 相关问题批量修复 | ≥0.75 |
| COLLABORATIVE_FIX | 协作修复，AI与人工共同完成 | 关键功能、安全问题 | ≥0.6 |
| AUTOMATIC_FIX | 自动修复，AI独立完成 | 简单问题、重复性任务 | ≥0.85 |
| MANUAL_FIX | 人工修复，AI提供建议 | 复杂问题、架构决策 | <0.6 |

### 12.4 自动修复代码留底规则

所有自动修复的代码变更必须留底记录：

| 字段 | 类型 | 说明 | 必填 |
|------|------|------|------|
| fix_id | TEXT | 修复ID(唯一) | ✅ |
| file_path | TEXT | 修改的文件路径 | ✅ |
| original_code | TEXT | 修复前的原始代码 | ✅ |
| fixed_code | TEXT | 修复后的代码 | ✅ |
| error_type | TEXT | 错误类型 | ✅ |
| error_message | TEXT | 错误信息 | ❌ |
| fix_strategy | TEXT | 修复策略 | ✅ |
| confidence | REAL | 修复置信度(0-1) | ❌ |
| executed_by | TEXT | 执行修复的AI员工ID | ✅ |
| executed_at | TEXT | 修复执行时间 | ✅ |
| status | TEXT | 修复状态(pending/success/failed/rolled_back) | ✅ |
| rollback_available | INTEGER | 是否可回滚(1=可回滚) | ❌ |

### 12.5 回滚机制

```python
def rollback_fix(fix_id):
    """回滚指定修复"""
    # 1. 查询修复记录
    record = get_fix_record(fix_id)
    
    if not record or record['status'] != 'success':
        return {'success': False, 'reason': '未找到可回滚的修复记录'}
    
    if record['rollback_available'] != 1:
        return {'success': False, 'reason': '该修复不支持回滚'}
    
    # 2. 恢复原始代码
    with open(record['file_path'], 'w', encoding='utf-8') as f:
        f.write(record['original_code'])
    
    # 3. 更新状态
    update_fix_status(fix_id, 'rolled_back')
    
    return {'success': True, 'message': '回滚成功'}
```

### 13.2 修改中规范
